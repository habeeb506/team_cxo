# Architecture

This document explains the folder structure and the reasoning behind it. The
goal throughout: adding a new module (auth, notifications, dashboards,
reports, analytics, or anything else) should mean *adding files inside
existing folders*, never restructuring what's already there.

## Backend (`backend/src/`)

Request flow: `routes` -> `middlewares` (auth, validation) -> `controllers` -> `services` -> `repositories` -> MongoDB.

| Folder | Purpose | Why it exists |
|---|---|---|
| `config/` | Env loading (`index.js`), app constants (`constants.js`), Mongo connection (`db.js`) | One source of truth for environment and app-wide values -- never read `process.env` outside this folder |
| `routes/v1/` | Thin Express routers, one file per resource | Versioned (`/api/v1`) so a `v2` or a separate client-facing API can be added later without breaking existing consumers |
| downstream bulk routes | Every resource router also registers `POST /import` and `POST /bulk-delete`, both validated by the one shared `validations/common/bulkImport.schema.js` / `bulkDelete.schema.js` | Backs the frontend's CSV import and bulk-delete features (see "Management pages" below) without duplicating per-record validation/uniqueness logic |
| `controllers/` | Parses `req`/`res`, calls a service, formats the response | `baseController.js` provides `createCrudController(service)` -- a full CRUD controller for a new resource in one line |
| `services/` | Business logic and orchestration | `BaseService.js` provides default CRUD business logic -- including `bulkCreate`/`bulkDelete`/`replaceAll`, which reuse the existing single-record `create`/`delete` so bulk operations get the exact same validation, uniqueness checks, and soft-delete behavior as single-record ones -- feature services extend it and override only what's actually custom (e.g. `CxoPermissionService` overrides `list`/`getById` to populate `member`) |
| `repositories/` | The only layer that touches Mongoose | `BaseRepository.js` provides generic paginated CRUD over any model, **and is the single place soft-delete is implemented** (`softDeleteById`/`softDeleteMany`/`restoreById`/`withDeletedFilter`) -- keeps persistence details swappable without touching services |
| `validations/` | Zod schemas per resource, plus `common/` for shared ones (`objectId`, `pagination`, `bulkDelete`, `bulkImport`) | Validation rules live next to each other, separate from the middleware that executes them |
| `middlewares/` | Cross-cutting Express concerns: `errorHandler`, `notFound`, `requestLogger`, `validateRequest`, `auth.middleware.js` (`requireAuth`) | Registered once in `app.js` (except `requireAuth`, mounted per-router in `routes/v1/index.js` -- see "Authentication" below); a future `authorize.middleware.js` (role/permission checks) slots into the same chain |
| `models/` | Mongoose schemas, `plugins/auditableSchema.plugin.js` for shared audit/soft-delete *fields* | See "Data layer" below for the current collections |
| `events/` | `eventBus.js` -- a tiny internal pub/sub | Services can `emit()` domain events (`user.created`) without knowing who listens; a future notifications service just `.on()`s the event -- no existing service is touched |
| `utils/` | `logger`, `ApiError`, `asyncHandler`, `apiResponse`, `pagination` | Small, generic helpers used everywhere; prevents duplicated error/response/pagination logic per route |

Adding a feature (example: "reports"): `models/report.model.js` ->
`repositories/ReportRepository.js extends BaseRepository` ->
`services/ReportService.js extends BaseService` ->
`controllers/report.controller.js` (via `createCrudController`, plus any
custom aggregation endpoints) -> `validations/report.schema.js` ->
`routes/v1/report.routes.js`, registered in `routes/v1/index.js`. Nothing
above that list changes.

## Frontend (`frontend/src/`)

| Folder | Purpose | Why it exists |
|---|---|---|
| `api/` | `httpClient.js` (shared axios instance, `withCredentials: true` so the session cookie rides along), `baseApiService.js` (`ApiService` base class), `api/services/` (one class per CRUD resource, plus `authApiService.js`/`healthApi.js`/`teamRosterApiService.js` for non-CRUD endpoints) | One HTTP client with shared config/interceptors. Two deliberately different patterns: a CRUD resource gets an `ApiService` subclass; a one-off endpoint (health, auth, team roster) gets a plain class/function instead -- forcing the latter into a class with unused `create`/`update`/`delete` methods would be worse, not more consistent |
| `hooks/` | `useApiResource`, `useMutation`, `useFetch`, `useInfiniteList`, `usePagination`, `useForm`, `useDebounce`, `useToggle`, `useToast`, `useRowSelection`, `useCsvExport`, `useCsvImport`, `useCsvTemplate`, `useManagementPageState`, `useAuth`, `useYearMonthFilter`, `useClickOutside`, `useTaskStatusUpdate`, `useTaskStatusSync` | Generic, feature-agnostic state logic reused by every future page instead of re-implemented per component -- see "Frontend data layer", "Management pages", and "Authentication" below |
| `components/ui/` | `Button`, `Input`, `Select`, `MultiSelect`, `CheckboxGroup`, `Card`, `Spinner`, `Alert`, `Modal`, `ConfirmDialog`, `EmptyState`, `DataTable`, `SearchBar`, `PaginationControls`, `StatusBadge` | Pure presentational primitives; every future page is composed from these, not new one-off markup |
| `components/layout/` | `Header`, `TopNav`, `Footer` | The chrome around every internal page; a new nav item is one entry in `TopNav.jsx`. `Header` shows the real signed-in user + logout (see "Authentication" below) |
| `components/management/` | `ManagementPage`, `ManagementToolbar`, `RecordFormModal`, `RecordViewModal`, `DynamicFormFields`, `ImportResultModal` | The generic, config-driven CRUD page -- see "Management pages" below |
| `components/quickLinks/` | `QuickLinksGrid`, `QuickLinkCard` | The tile grid rendered on `pages/QuickLinksPage.jsx` for modules without a real page yet |
| `components/dashboard/` | `NewsBulletinPanel` + `NewsBulletinModal`, `OpenTasksPanel`, `IndividualContributionPanel` + `individualContributionColumns.jsx`, `LeaderboardPanel`, `KpiCard`, `YearMonthFilter`, `TaskStatusSelect`, `taskDetailFields.js` | Dashboard-only widgets -- see "Dashboard layout" below |
| `components/ErrorBoundary.jsx` | Catches render errors app-wide | One broken widget can't blank the whole app |
| `features/<resource>/` | Per-resource config only -- `*.management.config.js` (columns, form fields, CSV mapping), `*.constants.js` (option lists mirroring backend enums), and resource-specific extras (`tasks/TaskCompletionBadge.jsx`; `cxoTeams/TeamRosterStatsBar.jsx` + `useTeamRosterUpload.js`) -- currently `cxoTeams/`, `businessTeams/`, `cxoPermissions/`, `tasks/` | Keeps `components/management/` purely generic while each module's actual shape (its fields, columns, CSV headers, and any bespoke UI like the roster stats bar) lives next to each other. `TaskCompletionBadge` specifically lives here rather than in `components/dashboard/` so both the Tasks admin page's config and the Dashboard's Individual Contribution columns can import it without an awkward features-importing-from-dashboard-components direction -- see "Task completion timeliness" below |
| `layouts/` | `MainLayout` (header + top nav + content, for the internal app, pinned via `h-screen`/`overflow-hidden` so only the content region scrolls), `AuthLayout` (centered, for `/login`) | A new page picks a layout in `routeConfig.js`; no new layout code needed |
| `context/` | `ToastContext`, `AuthContext` | App-wide transient notifications and the real authentication session (see "Authentication" below) |
| `routes/` | `routeConfig.js` (data-driven route list), `AppRoutes.jsx` (renders from it), `ProtectedRoute.jsx` (a real auth guard) | Adding a route is one entry in `routeConfig.js`; a route's group sets `protected: true`/`false` |
| `constants/` | `apiEndpoints.js`, `routePaths.js`, `quickLinks.js`, `dateFilters.js` | No hardcoded path strings anywhere in the app |
| `utils/` | `cn.js` (class merging), `apiCache.js` (in-memory TTL cache, also used for request de-duplication -- see below), `formatDate.js` (shared date/time formatting), `taskEvents.js` (minimal pub-sub for cross-widget task-status sync -- see "Dashboard layout" below), `csv.js` (plain-text CSV template/export/import, dependency-free), `excelTemplate.js` (real `.xlsx` template/import via `exceljs`, for the one field that needs an actual clickable dropdown -- see "Team roster" below) | Small helpers shared by UI components and hooks |
| `public/favicon.svg` | The app's favicon (referenced from `index.html`'s `<link rel="icon">`) -- a plain rounded-square "T" mark | Every other frontend scaffold ships Vite's default `vite.svg`; this replaces it with something app-specific |

Adding a feature (example: "reports"): `api/services/reportApiService.js` (3-line
`ApiService` subclass) -> `features/reports/report.management.config.js` ->
`pages/ReportsPage.jsx` (renders `<ManagementPage config={...} />`) -> one
entry each in `constants/routePaths.js`, `routes/routeConfig.js`, and
`components/layout/TopNav.jsx`. Nothing else changes -- see "Management
pages" below for the full pattern.

## Frontend data layer

**`ApiService`** (`api/baseApiService.js`) is the frontend mirror of the backend's `BaseRepository`/`BaseService`: a resource's entire HTTP client is a subclass declaring only its base path (see `api/services/cxoTeamApiService.js`). `getAll` forwards params straight through as query string, so it lines up with the backend's pagination/filter/search query shape with no translation layer.

**`useApiResource(apiService, options)`** (`hooks/useApiResource.js`) is the one hook every list/table page is built on: it fetches through the given `ApiService` and briefly caches responses (`utils/apiCache.js`, a deliberately small in-memory TTL cache -- a seam for a real caching library later, not a replacement for one). Page/limit state is delegated to `usePagination` (`hooks/usePagination.js`) rather than re-declared inline, so the same pagination primitive is available standalone for a future client-side-only list that doesn't go through an `ApiService`. A future module's list page changes only the `apiService` instance passed in.

**`useFetch(fetcher, deps, options)`** (`hooks/useFetch.js`) is the lighter-weight counterpart for a single one-off request (health check, a leaderboard period) rather than a paginated list. Pass `{ cacheKey, cacheTtlMs }` to reuse the same `apiCache.js` TTL cache `useApiResource` uses -- and `useFetch` also de-duplicates concurrent in-flight requests for the same `cacheKey`, so two components that both call a hook built on it at the same time share one network request instead of firing a duplicate.

**`useMutation(fn)`** (`hooks/useMutation.js`) wraps create/update/delete calls with `isLoading`/`error` state and rethrows on failure so callers can react (show a toast, keep a modal open). `hooks/useForm.js`'s `handleSubmit` catches that rethrow and maps the backend's `ApiError.details` (`{ field, message }[]`) onto the right form field automatically -- this only works because `httpClient.js`'s error interceptor preserves `details`/`statusCode` on the thrown `Error` instead of discarding them.

## Management pages

Team Members, Business Teams, Permissions, and Tasks are full CRUD pages (create, edit, view, delete, search, filter, pagination, CSV import/export, bulk delete) built entirely from **one generic component plus a config object** -- no page hand-rolls fetching, modals, or bulk-action wiring.

**`useManagementPageState(config)`** (`hooks/useManagementPageState.js`) is the single stateful hook behind every management page. It composes the hooks already described above -- `useApiResource` (list/pagination/filter/search), `useMutation` x4 (create/update/delete/bulk-delete), `useRowSelection`, `useCsvExport`, `useCsvImport`, `useCsvTemplate`, `useToggle` x4, `useToast` -- into one state object. `config` is `{ apiService, resourceLabel, emptyValues, fields, csv, getRowId?, mapRecordToFormValues?, transformSubmitValues?, getRowLabel?, templateLabel?, formClassName? }`; `mapRecordToFormValues`/`transformSubmitValues`/`getRowLabel` are optional escape hatches for a resource whose record shape doesn't map 1:1 onto its form (see Permissions below). `templateLabel` overrides `ManagementToolbar`'s default "Download Template" button text (passed straight through as a `downloadTemplateLabel` prop) -- most resources leave it unset; Team Members sets it to "Download Team Template" since that page also has its own separate "Download Roster Template" button (see "Team roster" below), where the generic label alone would be ambiguous about which template it downloads.

**`ManagementPage`** (`components/management/ManagementPage.jsx`) is the presentational half: it calls `useManagementPageState(config)` and renders `ManagementToolbar` (search + filter dropdowns + Add/Template/Import/Export/bulk-delete buttons) + `DataTable` (selectable, with an auto-appended View/Edit/Delete actions column) + `PaginationControls` + `RecordFormModal` (create/edit) + `RecordViewModal` (read-only detail) + two `ConfirmDialog`s (single delete, bulk delete) + `ImportResultModal`. A resource's page is just: build a `config`, render `<ManagementPage title=... columns={...} filters={...} config={config} />`.

**`fields`** is the one config array that drives both the create/edit form (via `DynamicFormFields`, which renders `text`/`email`/`number`/`date`/`select`/`multiselect` inputs from `{ name, label, type, options?, required? }`) and the read-only view modal -- a resource never maintains two separate field lists. A field can also be marked `computed: true` (e.g. Team Members' `overallExperience`/`firmExperience`/`timeInRole`, see below) -- `DynamicFormFields` skips it entirely (never renders it as an input, since a server-derived value can't be submitted back), while `RecordViewModal` still shows it read-only like any other field, since it applies no such filter.

**CSV import/export/template** is generic on both ends: `utils/csv.js` has no external dependency (`parseCsv` handles quoted/comma/newline fields by hand; `fetchAllRecords` pages through the full result set so export isn't capped at one page; `buildCsvTemplate` builds a downloadable header row, optionally with one example row). A resource supplies `csv: { exportFields, filenamePrefix, mapImportRow, templateSampleRow? }` -- the same `exportFields` list doubles as the template's columns, so there's no separate header list to maintain. `mapImportRow` adapts raw CSV string columns into a create payload. Import actually persists through the backend's bulk endpoints (`POST /import`, `POST /bulk-delete`), not N sequential client-side requests.

**Validation, duplicates, and per-row error reporting**: the route-level `bulkImportSchema` only checks that `records` is a non-empty array of objects -- it deliberately does *not* validate each record's exact shape, so one malformed CSV row can't reject the entire file before any row is even looked at. Real per-record validation happens one row at a time inside `BaseService.bulkCreate` (via `this.create()` -> `this.validateRecord()`, which runs the resource's own zod `bodySchema` -- the same schema a single-record POST uses) and duplicate prevention runs the same way (`assertUnique`, checked per row, so a duplicate against the database *or* against an earlier row in the same file is caught identically). A bad row is skipped and reported -- `{ row, message, details }` -- while every valid row still gets inserted; `ImportResultModal` (`components/management/ImportResultModal.jsx`) surfaces that list to the admin with the exact row number and reason, automatically, whenever an import has any failures.

**Append vs. replace**: `POST /import` accepts `mode: 'append' | 'replace'` (default `append`). `replace` calls `BaseService.replaceAll`, which soft-deletes every existing record for that resource (`BaseRepository.softDeleteMany`) and then runs the normal `bulkCreate` -- nothing is physically destroyed, so it's reversible by an administrator and fully audited like every other delete in this app. This is why `CxoTeam.emailId`/`empIdNew`/`empIdOld`, `BusinessTeam.emailId`, and `CxoPermission`'s `member+resource` compound index are all declared as **partial unique indexes** scoped to `{ isDeleted: { $ne: true } }` instead of plain `unique: true` -- a plain unique index is enforced across soft-deleted documents too, which would make "replace with the same emails" fail with a database-level duplicate-key error even though the app's own uniqueness check already ignores deleted rows. `ManagementToolbar` exposes the choice as a small mode selector next to the Import button and confirms before a `replace` actually runs, since it's the one destructive option.

**Reference implementation -- Team Members** (`pages/TeamHierarchyPage.jsx` + `features/cxoTeams/cxoTeam.management.config.jsx`): the simplest CRUD case in terms of wiring (static fields/columns/filters, no cross-resource lookups), though its **table** is deliberately the narrowest of any resource -- `CXO_TEAM_COLUMNS` shows only Name, Location, Place/Floor, Shift, Support, Time Slot (by request), while `CXO_TEAM_FIELDS` (the create/edit form) captures every other business field the underlying `cxo_teams` document has -- the table was trimmed for at-a-glance readability, not the record itself, and `emailId`/`empIdNew` are still required for uniqueness regardless of whether they're shown as columns. By request, `CXO_TEAM_FIELDS` also carries a full career/development profile block alongside the original identity/org/roster fields (Career Level, Prior/Firm/Overall Experience, Date Of Joining, Last Promotion, Time In Role, Backup Team Member, Coach, Primary/Secondary/Other Portfolio, Learning Hours, Business Chemistry, Certifications Planned, CE Baseline, Mobile#) -- added on top of the existing structure, not a replacement for any of it (in particular Location/Place/Group/Designation/Shift/Support/Time Slot, and the roster/schedule features built on the last three, are all unchanged). `empIdOld`/`empIdNew` are numeric (`type: 'number'`), not the free-text-with-prefix strings ("EMP2003", "LEGACY-1005") they used to be. `overallExperience`, `firmExperience`, and `timeInRole` are declared with `computed: true` -- a small generic addition to `DynamicFormFields`/field configs (see "Management pages" above) meaning "read-only, server-derived, never rendered as an editable input" -- since none of the three are stored fields (see CxoTeam.model.js's docblock and CxoTeamService.attachExperienceFields); they're still visible in the read-only View modal like any other field. By request, the exported/imported **CSV template** (`CXO_TEAM_EXPORT_FIELDS`) deliberately does *not* mirror the table -- it covers the opposite set: every settable identity/org/profile field, none of Support/Shift/Time Slot (roster-driven, belongs to the separate Team Roster template instead -- see "Team roster" below) and none of the three computed fields (nothing writes to them directly, so there's nothing to bulk-import). `designation` is `required` again at every layer (model, zod, and the CSV template) after briefly being relaxed to optional in an earlier iteration where the CSV didn't collect it. This is also the one resource whose config file is `.jsx`, not `.js` -- see "Team roster" below for why. The page itself is no longer *just* `<ManagementPage />`, either: it renders the roster stats bar and upload control described in "Team roster: monthly upload and stats bar" below, plus a List/Schedule view toggle (see "Weekly schedule grid" below) -- all three composed above/around the generic component rather than reaching into it, so `ManagementPage` itself stays exactly as reusable as it was.

**Business Teams** (`pages/BusinessTeamsPage.jsx` + `features/businessTeams/businessTeam.management.config.js`): same shape with no filter dropdowns, since `business`/`location`/`room` are free text rather than fixed enums -- search covers it instead. `BUSINESS_TEAM_COLUMNS` deliberately omits `createdAt`/`updatedAt` (hidden by request) even though the underlying `business_teams` document has them -- same "trim the table, keep the record" idea Team Members' column list above now also follows.

**Team roster: monthly upload and stats bar.** `CxoTeam.status` was originally an employment status, then repurposed into a daily availability status, then (by request) renamed to `CxoTeam.support`. Its value set has changed several times: briefly narrowed to a 5-value special-task-only field, widened back to 6 values including `available` again, then widened once more (by request) to 8 values with `pto`/`epto` added -- `available` / `training` / `reconciliation` / `mfa` / `dlaunch` / `pto` / `epto` / `other` (`TEAM_MEMBER_SUPPORT_TYPES` in `config/constants.js`; `available` is the everyday, nothing-special-to-report state and this field's default, `pto`/`epto` cover a person being off -- regular Paid Time Off vs. emergency/short-notice ePTO -- and `other` is the catch-all for anything that isn't one of the other six). Every uploaded day gets exactly one of these eight values -- `shift` (e.g. "9:00 AM to 6:00 PM", the person's regular working hours) and `timeSlot` (e.g. "9:00 AM - 1:00 PM" or "Full day", the time range the *current support value specifically* applies to -- every entry is paired with one) are unchanged free-form fields. None of `support`/`shift`/`timeSlot` are edited by hand day-to-day -- all three are kept in sync with a `team_roster_entries` collection (one row per person per calendar day) via a monthly roster upload: `TeamHierarchyPage.jsx` renders a "Download Roster Template" button next to it, downloading a real **.xlsx** workbook (`utils/excelTemplate.js`'s `downloadExcelTemplate`, via the `exceljs` package -- not the app's plain-text CSV template system) with "Employee Email"/"Date"/"Support"/"Shift"/"Time Slot" columns, where the Support column carries an actual clickable Excel dropdown (native list-type cell data validation, applied down 500 rows) constrained to `CXO_TEAM_SUPPORT_OPTIONS`'s labels -- a plain CSV file has no concept of cell-level validation, so a CSV template could only ever document the valid values in a comment, never actually offer them as a dropdown. The "Upload Monthly Roster" button (`features/cxoTeams/useTeamRosterUpload.js`) accepts either that filled-in `.xlsx` back (parsed with `utils/excelTemplate.js`'s `parseExcelFile`) or a plain `.csv` (`utils/csv.js`'s `parseCsv`, same as every other CSV import) -- chosen by the uploaded file's extension -- and both parsers return the identical shape, so the row-mapping and `POST /team-roster/import` call downstream don't care which format was uploaded. `TeamRosterService.importRoster` resolves each row's email to a `CxoTeam._id`, upserts the (member, date) row (`TeamRosterEntryRepository.upsertEntry` -- a *re*-upload for the same month overwrites rather than erroring, unlike every other resource's plain-insert CSV import), and a bad row (unknown email, invalid date/support value) is collected and reported per-row rather than failing the whole file, the same pattern every other import in this app follows. After import, `TeamRosterService.syncCurrentSupport` copies each touched member's *true* latest entry back onto `CxoTeam.support`/`shift`/`timeSlot`, which is what lets the Team Members table show "today's" value directly from `cxo_teams` without joining the roster on every list request -- rendered as its own colored `StatusBadge` column, separate from the Time Slot column next to it.

The stats bar above the Team Members table (`features/cxoTeams/TeamRosterStatsBar.jsx`, labeled "Roster Snapshot") reads `GET /team-roster/stats?period=day|week|month&date=...` (`TeamRosterService.getStats`) and shows Total Team (the live `cxo_teams` headcount, independent of period) plus, for the selected day/week/month, how many *distinct* people had each support value at least once in that range (`TeamRosterEntryRepository.getDistinctMembersBySupport` -- someone on Reconciliation for three days of the selected week counts once, not three times, since "how many people were on Reconciliation this week" is a headcount question, not a days-consumed one). `utils/date.js`'s `resolvePeriodRange` resolves the three period shapes: a single day, a Monday-Sunday ISO week, or a calendar month. `TeamRosterService` is a documented exception to the one-service-owns-one-repository rule (same shape as `TaskService`'s `HolidayRepository` dependency) -- it holds a `CxoTeamRepository` directly to resolve emails and write back synced support, since a full `CxoTeamService` call wouldn't fit either operation.

`backend/scripts/seeders/seedTeamRoster.mjs` seeds a month-to-date roster (every day from the 1st of the current month through today, for every seeded `cxo_teams` member, weighted mostly `available` with occasional special-task values) so the stats bar has real variety on a fresh `npm run seed` without anyone uploading a CSV first.

**Weekly schedule grid (MS Teams Shifts-style).** `TeamHierarchyPage.jsx` has a small List/Schedule toggle above the table -- "List" is the existing `<ManagementPage />` CRUD table (search/filter/pagination/CSV/bulk-delete/Add/Edit/Delete, unchanged), "Schedule" is a new read-only view (`features/cxoTeams/TeamShiftsGrid.jsx`): one row per team member, one column per day Monday-Sunday, each cell a colored `StatusBadge` with that day's `timeSlot` underneath (or a blank dash on a day that was never uploaded), plus Prev/Today/Next week navigation. It's additive, not a replacement -- nothing about the CRUD table changed, so no admin capability was traded away for the new view. Data comes from a new endpoint, `GET /team-roster/schedule?date=YYYY-MM-DD` (`TeamRosterService.getWeeklySchedule`, reusing the same `resolvePeriodRange('week', date)` the stats bar's "Week" period already uses, so a person's schedule always lines up with the same Monday-Sunday boundaries as the rest of the page), backed by a new repository method (`TeamRosterEntryRepository.findByDateRange`, `.populate('member', 'name')` so the grid gets each entry's name without a second lookup). The frontend combines that with a full, unpaginated `GET /cxo-teams?limit=100` fetch (`TeamShiftsGrid` needs every member as a row, not one page of 20 -- 100 is the backend's list-endpoint cap, see `PAGINATION_DEFAULTS.MAX_LIMIT` in `config/constants.js`; a `limit` above that 400s instead of returning data, a bug this grid originally had) and keys the week's entries into a `member|date` -> entry map for O(1) per-cell lookups. As with the stats bar, this view is read-only -- editing a day's support/shift/timeSlot still happens through the monthly roster CSV upload, not by clicking a cell.

**Modal scrolls internally; a resource can opt into a wider one.** `components/ui/Modal.jsx`'s dialog box is capped at `max-h-[85vh]` with `flex flex-col` -- the title and footer stay fixed (`flex-shrink-0`) while only the middle content area scrolls (`overflow-y-auto`). Previously nothing capped the box's height, so a long enough `fields` list (Team Members' form, once it grew to include Support *and* Time Slot on top of every other field) could render taller than the viewport with no way to scroll down to its own remaining fields or Save/Cancel buttons. `RecordFormModal` also accepts an optional `className`, forwarded straight to `Modal`, which `ManagementPage` reads from `config.formClassName` -- most resources leave it unset and get `Modal`'s default `max-w-md`; Team Members sets `formClassName: 'max-w-lg'` (`TeamHierarchyPage.jsx`) since `CXO_TEAM_FIELDS` is one of the longest field lists of any resource. Both changes are general-purpose (every modal in the app scrolls now; any future resource can widen its own form the same way), not one-off fixes scoped to Team Members.

**Permissions** (`pages/PermissionsPage.jsx` + `features/cxoPermissions/cxoPermission.management.config.js`) is the one case needing extra wiring, and demonstrates the escape hatches:
- The `member` field's options come from the live `cxo_teams` roster, fetched in the page via `useApiResource` and passed into `buildCxoPermissionFields(memberOptions)` -- a builder function instead of a static export, since the options aren't known until the roster loads.
- The backend populates `member` on read (`CxoPermissionService.list`/`getById`), so a record's `member` is an object when *viewing* but must be a raw id string when *editing*; `config.mapRecordToFormValues` unwraps `record.member?._id || record.member` before the edit form opens.
- CSV import needs to resolve a human-readable "Member Email" column back into an `ObjectId`; the page builds an `emailToId` lookup from the same roster and passes it into `buildCxoPermissionCsvConfig(emailToId)`.
- An empty `expiresAt` (optional date) would fail the backend's `z.coerce.date().optional()` validation -- an empty string isn't treated as "absent," it's coerced into an invalid `Date` and rejected. `config.transformSubmitValues` normalizes `''` to `undefined` right before every create/update call.

**Tasks** (`pages/TasksPage.jsx` + `features/tasks/task.management.config.js`) is a second case needing the Permissions-style roster lookup, and is also the app's worked example of upgrading a read-only resource into a full one (see CONTRIBUTING.md's "Read-only resources" section): `tasks` shipped for the Dashboard first (read-only, `GET` only), then gained `validations/task.schema.js`, the remaining CRUD routes, and this page once assigning tasks to people needed a real UI.
- `assignedTo` is a select of the `users` roster (not `cxo_teams` -- tasks were already scoped to `User` via the Dashboard's Individual Contribution/Open Tasks panels, so assignment reuses that same link rather than introducing a second "person" concept). The roster comes from a `GET /users` list route (`userController.getAll`), alongside the existing `/:id` route.
- `TaskService.list`/`getById` populate `assignedTo` (`name email jobTitle`) the same way `CxoPermissionService` populates `member` -- the Dashboard's own task queries are unaffected since neither Open Tasks nor Individual Contribution renders `assignedTo` (they're already scoped to one person).
- CSV import resolves an "Assignee Email" column back into an `ObjectId` via the same `emailToId` pattern Permissions uses.

Every future module (Applications, Floor Leaders, ...) follows this same pattern: a `*.management.config.js`, a thin page, and -- only if the resource needs it -- a `mapRecordToFormValues`/`transformSubmitValues` override. `ManagementPage`, `useManagementPageState`, and the shared UI kit never change.

## Authentication

Team Members, Business Teams, Permissions, and Tasks are reached directly from `components/layout/TopNav.jsx`'s top-level nav (not nested under Quick Links). Quick Links (`pages/QuickLinksPage.jsx`, `constants/quickLinks.js`) is a separate tile grid for the remaining planned modules that don't have a real page yet -- each tile points at `pages/ModulePlaceholderPage.jsx` (via `constants/routePaths.js`'s `modulePattern`) until it does; Team Hierarchy's and Tasks' tiles already point at their real routes instead, since both got a real page.

**Email-OTP login, no passwords.** Every seeded `user` logs in for real: enter an email (`POST /auth/request-otp`), receive a 6-digit code, submit it (`POST /auth/verify-otp`) within `OTP_EXPIRES_IN_MINUTES` (default 5) and `OTP_MAX_ATTEMPTS` (default 5) tries. This replaced an earlier mock "logged in as" switcher that let the frontend claim to be any seeded user with zero verification -- including reading other users' ticket/task data via a client-supplied id (see "Dashboard layout" below for how that hole was closed). `backend/src/models/AuthOtp.model.js` stores only a salted SHA-256 hash of the code (`backend/src/utils/otp.js`), never the code itself, with a TTL index that auto-expires old codes. `AuthService.requestOtp` responds identically whether or not the email is registered, so the endpoint can't be used to enumerate valid accounts.

**JWT via httpOnly cookie, no new dependencies.** `backend/src/utils/jwt.js` is a small, self-contained HS256 JWT implementation on Node's built-in `crypto` module (HMAC-SHA256) rather than the `jsonwebtoken` package -- deliberately narrow (only HS256, `alg` is never read from the token itself) so there's no algorithm-confusion surface to worry about. `verifyOtp` signs `{ sub, email, role }` and the controller sets it as an httpOnly, `sameSite: 'lax'` cookie (`AUTH_COOKIE_NAME` in `config/constants.js`) -- unreadable by page JS, so an XSS bug can't steal it the way `localStorage` token storage would allow. Reading it back doesn't need the `cookie-parser` package either -- `backend/src/utils/cookies.js` parses the raw `Cookie` header directly.

**`requireAuth`** (`backend/src/middlewares/auth.middleware.js`) verifies that cookie and attaches the *cryptographically verified* identity to `req.user` -- every controller reads `req.user.id` for "who is making this request" instead of trusting anything the client sends. It's mounted per-router in `routes/v1/index.js` (`router.use('/tasks', requireAuth, taskRoutes)`, etc.) rather than per-route, specifically so a new feature router registered there is protected automatically -- only `/health` and `/auth` are public. Authorization (restricting *what* an authenticated user can do, via `cxo_permissions`) is still a deferred next step -- see "Suggested improvements" below; today every authenticated user can use every route, same access level as before, just with a verified identity behind it now.

**OTP delivery: dev-mode logging or real SMTP, plus a temporary echo.** `backend/src/utils/mailer.js`'s `sendOtpEmail` has two paths, chosen by `OTP_DEV_MODE`: dev mode (the `.env.example` default, `true`) logs the code server-side instead of emailing it, so local login works with zero email setup; with `OTP_DEV_MODE=false` and `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` filled in, it actually emails the code via `nodemailer` (works with Gmail, Outlook/Office365, or any standard SMTP provider -- just env vars, see `config/index.js`). Independent of that choice, `config.otpEchoInResponse` (also `true` by default) controls whether the code is *also* echoed back in the `request-otp` response -- `pages/LoginPage.jsx` shows it as a hint whenever present, along with a `devNote` explaining whether it was emailed too. This lets real delivery be turned on and verified without losing the on-screen code as a fallback; set `OTP_ECHO_IN_RESPONSE=false` once real delivery is trusted, before this runs anywhere the response could be seen by anyone but the account owner.

**Mandatory device lock via `alias`, for the current locally-hosted deployment.** Every `User` carries an `alias` (`User.model.js`), auto-derived by a `pre('validate')` hook from the email's local part (`jane.doe@sample.com` -> `jane.doe`) whenever it isn't set explicitly, so every account gets a working value with no manual setup. `AuthService.verifyOtp` unconditionally requires the OS username the backend process is running under (`utils/machineIdentity.js`'s `getOsUsername`, Node's built-in `os.userInfo()`) to match `alias`, case-insensitively, for every account, checked *after* the OTP itself is confirmed correct so a wrong-device attempt never leaks anything about the account before the attacker even has a valid code. This isn't opt-in -- there's no way to disable it, only to correct which OS username an account expects. There's no admin UI for this yet (`users` is read-only -- see "Backend read-only resources" below), so overriding a specific account's `alias` (for someone whose real OS username doesn't happen to match their email prefix) is done via `npm run set-alias --prefix backend -- <email> <osUsername>` (`backend/scripts/setUserAlias.mjs`; `--reset` restores the email-derived default). Because the check is mandatory, `scripts/seeders/seedUsers.mjs` also auto-generates a pinned `Local Admin (<osUsername>)` account whose email's local part matches whatever OS username actually runs `npm run seed`, so every fresh seed guarantees at least one working login on the machine that seeded it, without needing to guess the real operator's email. **This only means anything while the backend runs locally, on the same machine as the person logging in** (today's deployment) -- `os.userInfo()` reports whichever OS account the Node process itself runs as, which is the actual signed-in user only when browser and backend share a machine. The instant this backend moves to a shared host (a real server, a container, anything reachable by more than one person), every visitor would see the *same* single service-account username, and this check would silently stop distinguishing anyone -- see `machineIdentity.js`'s docblock for what a real per-visitor device check would need instead (a client certificate, OS-level SSO/Kerberos, or an installed desktop agent). Don't carry `alias` values or this check into a real multi-user production deployment without first re-evaluating this -- it would lock out every account whose alias doesn't match the shared host's single OS username.

**Hostname allowlist, a separate access gate.** `middlewares/hostAllowlist.middleware.js` is mounted first in `app.js` -- before helmet, CORS, and every route, including the public `/auth/*` ones -- and rejects any request whose `Host` header isn't in `ALLOWED_HOSTS` (`.env`, parsed into `config.allowedHosts`). This is a coarse "how did this request reach the server" check, independent of `requireAuth`'s "who is making this request": it guards against DNS-rebinding-style traffic and stray requests hitting the API via a raw IP or an unapproved domain, applying equally regardless of authentication state. An empty `ALLOWED_HOSTS` disables the gate (fails open) rather than locking everyone out from a blank config -- `JWT_SECRET` being required is what prevents the app from starting with no security at all.

**Frontend session.** `context/AuthContext.jsx` (`useAuth()`) hydrates from `GET /auth/me` on load -- the answer comes from the verified cookie, never from anything stored client-side, so there's nothing for a user to tamper with to "become" someone else the way the old `localStorage`-based mock identity could be. `routes/ProtectedRoute.jsx` is a real guard now: it shows a spinner while that check is in flight, then redirects a signed-out visitor to `/login` (remembering the intended destination via router state) or renders the page. `routeConfig.js`'s `MainLayout` group is `protected: true`; the new `AuthLayout` group (just `/login`, `pages/LoginPage.jsx`) is `protected: false`, for the obvious reason that it's how a session is obtained in the first place. `components/layout/Header.jsx` shows the real signed-in user's name/role and a logout button, replacing the old machine-identity chip that displayed the OS user running the backend process as a stand-in identity.

## Dashboard layout

**Widgets never trust a client-supplied user id.** Before authentication existed, `OpenTasksPanel`/`IndividualContributionPanel` accepted a `userId` prop (from the mock identity) and asked the backend for `GET /tasks?assignedTo=<id>` -- any browser could see anyone's tickets/tasks just by changing that id client-side, since nothing verified it. Both panels now call `GET /tasks/mine` / `GET /tickets/mine` (`api/services/myTasksApiService.js` / `myTicketsApiService.js`) instead: `ticket.controller.js`'s and `task.controller.js`'s `getMine` handlers force `filter.assignedTo = req.user.id` from the verified session, ignoring any client-supplied `assignedTo` entirely. Neither panel takes a `userId` prop anymore -- whose data it shows is never this component's (or its caller's) decision to make. The general `GET /tasks`/`GET /tickets` list routes still accept `?assignedTo=<id>` as before, for the Tasks management page's broader "everyone's tasks" admin view -- that's intentionally in scope for any authenticated user today (see "Authentication" above). `appointments`, `vocs`, `shout_outs`, and `awards` (added for the Individual Contribution panel's four extra tabs) follow the exact same `getMine`/`/mine`/`my*ApiService.js` pattern -- see `appointment.controller.js`, `voc.controller.js`, `shoutOut.controller.js`, `award.controller.js` and their matching frontend services.

**Layout.** Open Tasks and News Bulletin sit in one 2-column row; Individual Contribution and Leaderboard sit in a second 2-column row below it (see `pages/DashboardPage.jsx`). Individual Contribution and Leaderboard each carry a Year/Month filter (`components/dashboard/YearMonthFilter.jsx` + `hooks/useYearMonthFilter.js`) -- News Bulletin doesn't, since it isn't scoped to a time period, and neither does Open Tasks anymore (see that panel's own paragraph below for why).

**Multi-select Year/Month filter.** Each axis is an independent `components/ui/MultiSelect.jsx` dropdown with a "Select all" checkbox (backed by `hooks/useClickOutside.js` for close-on-outside-click); Year and Month no longer have to be picked together the way the old single-select version required. Selecting nothing and selecting everything both mean "no restriction on that axis" (`hooks/useYearMonthFilter.js` collapses either case to an omitted query param). The backend (`utils/queryOptions.js`'s `buildListQueryOptions`) turns `?years=2024,2025&months=1,3` into a MongoDB `$expr` filter using the `$year`/`$month` date-expression operators, AND'd together when both axes are given -- this replaced an earlier `{ $gte, $lt }` single-range approach, since a range can't express a non-contiguous, multi-value selection. The Leaderboard follows the same shape: `LeaderboardEntryRepository.getLatestDateMatching({ years, months })` resolves the selection's most recent snapshot the same `$expr` way. A shared `?years=&months=` query shape (`validations/common/yearMonthQuery.schema.js`) is `.extend()`-ed into all three routes' schemas via zod, same pattern as before. `YearMonthFilter.jsx` also renders a "Clear all" link whenever either axis has an active selection, resetting both to "All" in one click.

**News Bulletin panel** (`components/dashboard/NewsBulletinPanel.jsx`) is lazy-loaded via `hooks/useInfiniteList.js` -- the accumulating-pagination counterpart to `useApiResource` (which replaces its page; this appends), reusable by any future activity/notification feed. Each item is clamped to 3 lines (Tailwind's `line-clamp-3`); "View more" opens `NewsBulletinModal.jsx` with the already-fetched full description -- no second request, since the list endpoint always returns the full text.

**Individual Contribution panel** (`components/dashboard/IndividualContributionPanel.jsx`) fetches the signed-in user's own records across six resources -- Tickets, Tasks, Appointments, VOCs, Shout-outs, Awards -- one `useApiResource` call each (against `myTicketsApiService`/`myTasksApiService`/`myAppointmentsApiService`/`myVocsApiService`/`myShoutOutsApiService`/`myAwardsApiService`, updated via `setFilters` whenever the Year/Month selection changes), and derives both the KPI cards and the active tab's table from that same fetched data. Every tab, including Tasks, applies no client-side status filter -- the complete history for that resource, cancelled/closed/resolved records and not-yet-finished tasks all included (`activeRows` in the panel is just the active resource's fetched data, as-is). Tasks used to be labeled "Completed Tasks" and filtered to `status === 'done'` only; it's now just "Tasks", the same full-history shape as every other tab -- Open Tasks (see that panel's paragraph below) remains the one place scoped to only what's still outstanding. A `TAB_DEFS` array pairs each tab with its api service, empty-state message, and a `summarize(rows)` function fed by that same `activeRows`, so a tab's KPI cards always match what's actually in its table; the two KPI cards always describe *whichever tab is currently active* (e.g. "Total Tasks" + "Completed" on the Tasks tab, "Total VOCs" + "Avg Rating" on VOCs) rather than staying fixed on any one pair regardless of what's being viewed. `DataTable` columns are looked up per tab from a `columnsByTab` map, all six of them static arrays from `components/dashboard/individualContributionColumns.jsx` (kept separate purely to keep the panel focused on data-fetching/layout) -- Tasks included, since this panel's Tasks tab is read-only (see the next paragraph). Unlike Open Tasks and Leaderboard (which default to "All"), this panel opts into `useYearMonthFilter({ defaultToCurrentPeriod: true })`, so it opens scoped to the current year/month rather than all-time.

**Task status editing is Open Tasks-only, with a server-owned completion timestamp and live cross-widget sync.** Only `components/dashboard/OpenTasksPanel.jsx` renders a task's Status column as a live `TaskStatusSelect` dropdown (`components/dashboard/TaskStatusSelect.jsx`); Individual Contribution's Tasks tab renders the same column read-only, via `TaskCompletionBadge` (`TASK_COLUMNS` in individualContributionColumns.jsx) -- a colored "Done" badge for finished tasks, falling back to a plain `StatusBadge` for todo/in-progress ones -- there is exactly one place in the Dashboard a task's status can be changed. `hooks/useTaskStatusUpdate.js` (used only by Open Tasks now) calls `taskApiService.update(id, { status })` -- the exact same `PATCH /tasks/:id` the Tasks admin page already uses (see "Management pages" above); there's no separate "quick edit" endpoint. Server-side, `TaskService.update` is overridden to stamp `Task.completedAt` with `new Date()` the instant `status` becomes `'done'`, and clear it back to `null` if status moves away from `'done'` again -- this is a fact the server derives, never something a client sends (`taskBodySchema` doesn't even define a `completedAt` field, so zod strips it from any request body before this logic runs), the same trust boundary already applied to `assignedTo` on the `/mine` endpoints.
  Individual Contribution still needs to reflect an edit made in Open Tasks *without a page reload* -- marking something 'done' there needs to update its Status badge on Individual Contribution's Tasks tab immediately (the row was already visible there; only its badge changes now). Two mechanisms work together on every successful update: `invalidateCache(resourcePath)` (`utils/apiCache.js`) drops the stale cached response so the *next* fetch returns fresh data, and `emitTaskStatusChanged()` (`utils/taskEvents.js`, a minimal in-memory pub-sub) tells every already-mounted widget to actually go fetch that fresh data right now. Both Open Tasks and Individual Contribution call `useTaskStatusSync(refetch)` (`hooks/useTaskStatusSync.js`) once, subscribing their own `refetch` to that event -- Individual Contribution can't *cause* the event (it never edits status), but it still needs to *react* to it. Cache invalidation alone wouldn't be enough (a refetch would just serve the same stale cached response back); the event alone wouldn't be enough either (the other widget would never know to refetch at all).

**Open Tasks panel** (`components/dashboard/OpenTasksPanel.jsx`) is deliberately a *different, leaner* view over the same `tasks` data Individual Contribution already fetches -- not a duplicate. It fetches the signed-in user's own tasks the same way, then filters client-side to `status === 'todo' || status === 'in-progress'` (only finished 'done' tasks are excluded) and sorts by `dueDate` ascending, since "open, most urgent first" isn't a query shape worth a new backend endpoint for. Overdue rows (`dueDate` in the past) are highlighted via `DataTable`'s `getRowClassName`. Unlike Individual Contribution and Leaderboard, it has **no** Year/Month filter -- "open" here is a status, not a time range, so a date filter couldn't narrow this view without changing what it means; it always fetches the user's full unfiltered task set and lets the todo/in-progress filter do the only narrowing that makes sense. Marking a task 'done' via its quick-edit Status column drops it out of *this* list, immediately, and updates its badge on Individual Contribution's Tasks tab (which already shows it either way) -- see the previous paragraph for how.

**Task detail View button, reusing the management-page modal.** Both Open Tasks and Individual Contribution's Tasks tab add a sticky-right View column (`Button` + `DataTable`'s `sticky: 'right'`, same pattern `components/management/ManagementPage.jsx`'s own action column uses) that opens `components/management/RecordViewModal.jsx` -- the exact same generic, read-only label/value modal the Tasks admin page's own View button already opens (see "Management pages" above), not a new one-off component. It's fed by `components/dashboard/taskDetailFields.js`'s `TASK_VIEW_FIELDS` rather than `task.management.config.js`'s full `buildTaskFields(assigneeOptions)`, since these two widgets already know whose task it is (`/tasks/mine`) and don't need an `assignedTo` field. Both widgets keep their own local `viewingTask` state (`useState`) -- there's no shared "currently viewed record" concept across widgets, same as there's no shared list state.

**Task completion timeliness -- green/yellow/red status coloring, weekend/holiday-aware.** A done task's Status badge is colored based on how it compares to its due date: green if completed at or before `dueDate`, yellow if completed late but within 24 *business* hours of it, red beyond that -- the badge text always just reads "Done" in every case (by request -- color alone carries the on-time/delayed/overdue meaning, `TaskCompletionBadge.jsx`'s `TIMELINESS_LABELS` maps all three outcomes to the same string) -- shown on both Individual Contribution's Tasks tab and the Tasks admin page, via the shared `features/tasks/TaskCompletionBadge.jsx` (falls back to the plain `StatusBadge` for any non-done status, or a done task with no due date to compare against). "Business hours" deliberately excludes Saturdays, Sundays, and the seeded holiday calendar -- a task that goes overdue at 4pm Friday and is finished 9am Monday has only accrued the Friday-4pm-to-midnight segment, not the whole weekend. The classification is computed **server-side**, never in the badge component itself: `backend/src/utils/businessTime.js`'s `calculateBusinessDelayMs` walks day-by-day from `dueDate` to `completedAt`, summing only the portions that fall on a working day, and `classifyCompletionTimeliness` turns that into `'on-time' | 'delayed' | 'overdue' | null`. `TaskService.list`/`getById` are overridden to call this (`attachCompletionTimeliness`) and attach the result as `completionTimeliness` on every task in the response, spreading each Mongoose document via `.toObject()` first -- the same "plain object + computed field" pattern `LeaderboardService.getEntriesForDate` already uses for `rank`, since a schema-less property set directly on a Mongoose document wouldn't survive its own `toJSON()` serialization. The holiday calendar comes from a new read-only `holidays` collection (`Holiday.model.js`: `occasion` + `date`, with `day` auto-derived from `date` in a `pre('validate')` hook so it can never drift out of sync) exposed at `GET /holidays` and seeded for 2026 by `backend/scripts/seeders/seedHolidays.mjs`. `TaskService` instantiates a `HolidayRepository` directly in its constructor to fetch that calendar -- a deliberate, narrow exception to the app's usual one-service-owns-one-repository rule, since a full `HolidayService` (which still exists, for `GET /holidays` itself) would add nothing to this internal, read-only lookup. `backend/scripts/seeders/seedTicketsAndTasks.mjs` cycles each seeded user's done tasks through all three outcomes (a due date safely in the past, `completedAt` placed a few hours before it, ~6 hours after it, or several days after it) so a fresh `npm run seed` shows real green/yellow/red variety instead of every done task landing on the same color.

**Leaderboard panel** (`components/dashboard/LeaderboardPanel.jsx`) uses the shared multi-select Year/Month filter (rather than a specific-date picker) and highlights/auto-scrolls to the signed-in user's own row (`useAuth()`, not anything client-tampered). This needed two small, generic additions to `components/ui/DataTable.jsx`: optional `getRowClassName(row)` and `getRowRef(row)`, both no-ops unless passed -- any future table wanting per-row styling or a scroll-to target reuses the same props instead of a new table implementation.

**Backend read-only resources.** `news_bulletins` and `tickets` follow the same model/repository/service layering as every other resource, but are deliberately read-only for now (no create/update/delete/import routes registered -- see each `routes/v1/*.routes.js`) since the Dashboard only needs to display them and inventing an admin UI for undefined requirements would be unnecessary complexity. `users` is similarly read-only aside from the plain `GET /` list route the Tasks management page's assignee picker needs. `tasks` used to be in this read-only list too until an admin UI was actually needed for it -- see "Management pages" above and CONTRIBUTING.md's "Read-only resources" section for that upgrade path, which `tickets` would follow identically if it ever needs the same treatment. `appointments`, `vocs`, `shout_outs`, and `awards` (backing Individual Contribution's four extra tabs) are read-only from day one, same reasoning -- `GET /` and `GET /mine` only, no admin UI planned yet. `leaderboard` is the one fully custom read endpoint: `LeaderboardService.getEntriesForPeriod` resolves a specific `date`, or a `years`/`months` selection's most recent snapshot, or (with neither) the latest snapshot overall, then computes rank at read time by sorting that snapshot's `leaderboard_entries` by `overallScore` (never stored -- see `LeaderboardEntry.model.js`), since a snapshot is small and bounded (100 people) rather than something a live aggregation needs to reconstruct.

## Data layer (MongoDB -- database `cxodb`)

Every collection is built on `models/plugins/auditableSchema.plugin.js`, applied via `schema.plugin(auditableSchemaPlugin)`. It adds `isDeleted`/`deletedAt` (soft delete), `createdBy`/`updatedBy` (audit trail, nullable until auth exists), `schemaVersion` (future migrations), and a free-form `metadata` object (escape hatch for fields that don't warrant a schema change yet) -- once, in one place, instead of every model re-declaring these fields. Combined with Mongoose's own `{ timestamps: true }` (`createdAt`/`updatedAt`), every collection has full audit coverage for free.

The plugin only adds *fields* -- it deliberately does not add Mongoose document methods or query helpers for soft delete. That behavior lives entirely in `BaseRepository` (`softDeleteById`, `softDeleteMany`, `restoreById`, and the `withDeletedFilter` helper that every read method merges into its filter), since repositories are the only layer allowed to touch Mongoose. Keeping soft delete in one place -- rather than splitting it between schema-level methods and repository-level filtering -- means there's exactly one way to soft-delete or query "including deleted" records, not two that could quietly drift apart.

**`cxo_teams`** -- the leadership/reporting-hierarchy roster. `lead` and `manager` are `ObjectId` references back into the same collection, which is what makes org-chart traversal (a member's direct reports, or their manager chain) possible without a separate hierarchy table. `emailId`, `empIdNew`, and `empIdOld` are each unique via a **partial unique index** scoped to `{ isDeleted: { $ne: true } }` (see "Append vs. replace" above) instead of a plain `unique: true` -- `empIdOld`'s partial filter also requires the field to exist, replacing what used to be a plain `sparse: true` (not every member has a legacy ID). `empIdOld`/`empIdNew` are `Number` (by request; previously free-text strings like "EMP2003"/"LEGACY-1005"). `level`, `careerLevel`, `group`, and `designation` are free-form strings rather than hardcoded enums, since org-level codes, career bands, group names, and job titles vary by company and change independently of the schema (`level` and `careerLevel` are two distinct fields -- an org-hierarchy code like "L1"-"L4" vs. a separate career/competency band like "Senior Manager"). `support` is a daily roster-status value (`TEAM_MEMBER_SUPPORT_TYPES`: `available`/`training`/`reconciliation`/`mfa`/`dlaunch`/`pto`/`epto`/`other`, defaults to `available`), and `shift`/`timeSlot` are free-form strings (regular working hours, and the time range the current support value applies to, respectively) -- all three are kept in sync with this person's latest `team_roster_entries` row rather than edited as independent facts; see "Team roster: monthly upload and stats bar" above.

By request, this document also carries a career/development profile block, added alongside every field above rather than replacing any of it: `priorExperience` (years before this firm, `Number`), `joiningDate` (`Date`, pre-existing but not previously exposed in the frontend), `lastPromotionDate` (`Date`, unset if never promoted), `backupTeamMember`/`coach`/`primaryPortfolio`/`secondaryPortfolio`/`otherPortfolio`/`businessChemistry`/`certificationsPlanned`/`ceBaseline`/`mobile` (all free-text strings), and `learningHours` (`Number`). Three more fields a user sees on this record -- `overallExperience`, `firmExperience`, and `timeInRole` -- are deliberately **not** part of this schema at all: they're derived from `joiningDate`/`priorExperience`/`lastPromotionDate` and computed fresh on every read by `CxoTeamService.attachExperienceFields` (`backend/src/utils/experience.js`'s `yearsBetween` helper) rather than stored, since a persisted "years of experience" value would silently go stale every single day -- the same reasoning `Task`'s `completionTimeliness` follows.

Indexes: `lead`, `manager` (hierarchy lookups), compound `group + level` (common dashboard filter), and a text index on `name + designation` (search). `backend/scripts/seeders/seedCxoTeams.mjs` seeds a 25-person, 4-level hierarchy (1 CEO -> 4 Directors -> 8 Managers -> 12 individual contributors) with pre-generated `_id`s so `lead`/`manager` can reference a person earlier in the same `insertMany` batch.

**`team_roster_entries`** -- one row per `cxo_teams` member per calendar day (`member`, `date`, `support`, `shift`, `timeSlot`), the historical record behind the roster stats bar's day/week/month counts; `cxo_teams.support`/`shift`/`timeSlot` only ever hold each person's *latest* entry. A partial unique compound index on `member + date` (scoped to non-deleted documents, same pattern as every other resource's uniqueness) means a re-uploaded roster for the same month upserts onto the existing rows instead of erroring as a duplicate. `date` is normalized to UTC midnight (`utils/date.js`'s `toUtcDateOnly`), the same whole-day-not-a-timestamp convention `leaderboard_entries.snapshotDate` uses. Read-only from the client's perspective aside from the roster upload endpoint (`POST /team-roster/import`) -- there's no per-row create/edit/delete UI. `backend/scripts/seeders/seedTeamRoster.mjs` seeds one month-to-date entry per member per day, weighted mostly `available`.

**`cxo_permissions`** -- grants a set of actions to a member on a named `resource` string (e.g. `cxo_teams`, `business_teams`, or `*` for global). Deliberately *not* modeled as one boolean field per permission type (`canCreate`, `canEdit`, ...) -- `actions` is an array of strings validated against `PERMISSION_ACTIONS` in `config/constants.js`. Adding a new permission type later (`approve`, `export`, `archive`) is a one-line addition to that constant; the schema and every existing document are untouched. A partial unique compound index on `member + resource` (scoped to non-deleted documents) both prevents duplicate grants and is the primary query pattern ("what can member X do on resource Y"); a single index on `resource` supports the reverse lookup ("who can access Y"). `expiresAt` supports time-bound grants without a separate table. `backend/scripts/seeders/seedCxoPermissions.mjs` seeds a representative spread of grants over the `cxo_teams` roster it's handed (a global grant for the CEO, roster/business-roster grants for each Director, ticket/task grants split across the Managers).

**`business_teams`** -- a business-unit roster, independent of `cxo_teams` (no reference between them -- a person can appear in both, linked only by the shared `emailId`, since the two collections represent different views of the org rather than a parent/child relationship). `emailId` is unique via the same partial-index pattern as `cxo_teams`. Also indexed on `business + location` (common filter) and a text index on `name`. `backend/scripts/seeders/seedBusinessTeams.mjs` seeds 25 members across 5 business units.

**`users`** -- real login accounts (see "Authentication" above; no password field -- email-OTP is the only credential). `role` (`USER_ROLES` in `config/constants.js`) is carried into the signed JWT on login but isn't enforced by any route yet (see "Suggested improvements" below). `lastLoginAt` is set on each successful OTP verification. `email` is unique via the same partial-index pattern as every other resource -- it's also the login identifier, looked up by `AuthService`/`UserRepository.findByEmail` on every OTP request. `alias` is the mandatory per-account device-lock identity, auto-derived from `email` -- see "Mandatory device lock via `alias`" above.

**`news_bulletins`** -- Dashboard announcements. `description` always holds the full text; truncating to a 3-line preview is a frontend display concern (`line-clamp-3`), not something the API does, so the "View more" modal never needs a second request. Indexed on `publishedAt` descending (latest-first is the only read pattern) and a text index on `title`.

**`tickets`** / **`tasks`** -- a person's raw activity log, scoped to them via `assignedTo` (`ObjectId` ref `User`). Deliberately separate from `leaderboard_entries` rather than the source of a live leaderboard computation -- see the next paragraph. Both indexed on `assignedTo + createdAt` (the Individual Contribution panel's read pattern) and `status`. `tasks.completedAt` is server-set only (see "Dashboard layout"'s "Task status editing is Open Tasks-only" paragraph above) -- `TaskService.update` stamps it the moment `status` becomes `'done'` and clears it otherwise, so it's never accepted as raw client input the way every other field on this collection technically could be through the Tasks admin page's edit form. `tasks` responses also carry a computed (never stored) `completionTimeliness` field -- see "Dashboard layout"'s "Task completion timeliness" paragraph above.

**`holidays`** -- the organization's yearly holiday calendar (`occasion` + `date`, with `day` auto-derived from `date` via a `pre('validate')` hook, never trusted as independent input). Read-only (`GET /holidays` only), not scoped to a user -- a holiday calendar applies to everyone equally, unlike `tickets`/`tasks`/etc. Indexed on `date`. Consumed by `TaskService.attachCompletionTimeliness` (via a direct `HolidayRepository` instance -- see "Task completion timeliness" above) to exclude these dates, alongside Saturdays/Sundays, when measuring how late a completed task was. Seeded for 2026 by `backend/scripts/seeders/seedHolidays.mjs`.

**`appointments`** / **`vocs`** / **`shout_outs`** / **`awards`** -- the four extra collections backing Individual Contribution's tabs, same `assignedTo` (`ObjectId` ref `User`) scoping pattern as `tickets`/`tasks`. `appointments.scheduledAt` + `status` (`APPOINTMENT_STATUSES`) track a person's meetings; `vocs.rating` (`VOC_RATING_RANGE`, 1-5) + `category` (`VOC_CATEGORIES`) capture Voice of Customer feedback attributed to whoever handled it; `shout_outs` and `awards` are simpler recognition records (`fromName`/`message`/`givenAt`, and `title`/`category`/`description`/`awardedAt`, respectively). Each is indexed on `assignedTo` plus its own primary date field, matching the panel's "this person's records, most recent/soonest first" read pattern.

**`leaderboard_entries`** -- one scored snapshot per user per date, not a live aggregation over `tickets`/`tasks`/etc. on every request. A snapshot gives the panel a stable, comparable "as of this date" view (with a Year/Month filter to look at earlier snapshots) for the cost of a cheap sort over a bounded collection (100 people), instead of reconstructing an expensive point-in-time aggregation across several collections on every page load. `overallScore` is a pre-computed weighted total (see `backend/scripts/seeders/seedLeaderboard.mjs` for the seed-time weighting); **rank is intentionally not stored** -- `LeaderboardService.getEntriesForPeriod`/`getEntriesForDate` sorts by `overallScore` and computes rank at read time, so it can never silently drift from the score the way a separately-stored rank field could. A partial unique compound index on `user + snapshotDate` prevents duplicate snapshots and is the primary query pattern.

**Validation** happens at two layers deliberately: zod schemas (`validations/`) reject bad input before it reaches a service, and Mongoose schema-level rules (`required`, `unique`, `match` against a shared `EMAIL_REGEX`, `enum`, `maxlength`) are the database's own last-line guarantee, independent of whatever validated the same rules upstream. `middlewares/errorHandler.js` normalizes whichever one catches a problem (a raw Mongoose `ValidationError`/`CastError`/duplicate-key error) into the same `{ success: false, message, details }` shape as a zod rejection, so API consumers never see two different error formats depending on which layer caught the issue.

**Scalability**: no collection hardcodes anything that's likely to change shape -- permission types, org levels, and future one-off fields all go through arrays/free-form strings/the `metadata` bag instead of new columns. Every collection is soft-deletable and audit-tracked from day one, so retention/compliance requirements later don't require a migration. Adding a new collection means one model file using the same plugin -- no changes to existing ones.

## What was deliberately left out

Authentication now exists (see "Authentication" above), but authorization
(restricting *what* a signed-in user can do, via `cxo_permissions`), rate
limiting, and notification templates don't yet -- only the generic scaffolding
that lets those be added later without restructuring. Authorization becomes an
`authorize.middleware.js` reading `cxo_permissions`, slotting into the same
chain `requireAuth` already does; notifications become an `eventBus`
subscriber; further dashboards/reports/analytics become new controllers +
pages built from the same base classes and UI kit already in place.

## Suggested improvements for long-term maintainability

Recommendations from the most recent architecture review, roughly in the
order they'll matter most as the app and team grow:

1. **Automated tests.** None exist yet on either side. Recommended stack:
   Vitest + React Testing Library for frontend hooks/components; Vitest (or
   Jest) + Supertest + `mongodb-memory-server` for backend route/service
   tests. `BaseService`/`BaseRepository`/`ManagementPage` are exactly the
   kind of shared, high-leverage code worth testing once and trusting
   everywhere else.
2. **CI pipeline** (GitHub Actions or equivalent) running `npm run lint` and
   the above tests on every push/PR for both packages -- currently lint-clean
   code depends entirely on a human remembering to run it.
3. **Pre-commit hooks** (husky + lint-staged) so ESLint/Prettier run before a
   commit lands, not just on demand.
4. **Rate limiting** (`express-rate-limit` or similar) on the backend,
   particularly the bulk-import and `/auth/*` endpoints, before this API is
   ever reachable from outside a trusted internal network. `AuthService`
   already enforces a per-email OTP request cooldown (`OTP_REQUEST_COOLDOWN_SECONDS`)
   and a max-attempts limit per code (`OTP_MAX_ATTEMPTS`), but that's
   per-email, not per-IP -- a proper rate limiter is still the right backstop
   against brute-forcing many different emails at once.
5. **API documentation** (OpenAPI/Swagger, generated from or alongside the
   existing zod schemas) once there's more than one frontend consuming this
   API, or any external integration.
6. **A real query cache** (React Query or SWR) to replace `utils/apiCache.js`
   -- already a deliberate, documented seam for exactly this swap, not a
   design that needs to be undone first.
7. **Migration tooling** (e.g. `migrate-mongo`) once `schemaVersion` bumps
   start actually happening -- the field exists today but nothing consumes
   it yet.
8. **Authorization (RBAC), on top of the authentication that now exists.**
   Every route already requires a verified session (`requireAuth` -- see
   "Authentication" above), but nothing yet restricts *what* a signed-in
   user can do once authenticated -- any authenticated user can read/write
   any resource today. `cxo_permissions` already models the shape a real
   authorization check needs (member + resource + actions); enforcing it
   means a new `authorize.middleware.js` reading that collection, mounted
   per-route (or per-router) alongside `requireAuth` -- no other file
   changes. Real SMTP delivery for OTP emails (`backend/src/utils/mailer.js`,
   currently dev-mode-only) is the other piece worth pairing with this.
9. **Correlation/request IDs** in `requestLogger`/`logger` once there is more
   than one backend instance, to make it possible to trace one request's
   logs across a load-balanced deployment.
10. **Rate-limit/paginate the leaderboard's snapshot growth.** `leaderboard_entries`
    grows by (participant count) per snapshot date -- fine at today's weekly
    cadence and 100 participants, but worth revisiting (e.g. archiving old
    snapshots) if the cadence increases or the population grows substantially.
